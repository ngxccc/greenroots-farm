# CI, Release & Automation Standards

## 1. Workflow Ownership

Each workflow owns one responsibility. A check runs in one workflow and nowhere else; other workflows consume its result.

| File           | Owns                                                          |
| :------------- | :------------------------------------------------------------ |
| `ci.yml`       | Version consistency, shared/tooling, API, and database gates. |
| `security.yml` | Trivy, `bun audit`, and CodeQL.                               |
| `release.yml`  | Version check, tag detection, and GitHub Release publishing.  |
| `labels.yml`   | `area:*` and `type:*` labels on pull requests.                |

- Do not re-run commands another workflow already owns. Reuse the job or rely on the required check.
- A `workflow_call` file needs two or more callers; a single caller inlines the jobs.
- Keep `name:` short and stable. Renaming a workflow renames every status check and breaks branch protection.

## 2. Area Labels

`area:*` describes which workspace a pull request actually changes, so it comes from `.github/labeler.yml`, not from the commit prefix.

- `area:storefront` and `area:backoffice` each require one changed file in that app outside the generated contract. `apps/*/src/types/api-schema.d.ts` is regenerated by `bun run types:sync`, so an API-only change that refreshes client types stays `area:api`.
- Generated contracts are still committed; they just do not count as consumer work. Label the source change, not the artifact.
- A new generated path joins the matching `!` exclusion in the change that introduces it.
- `type:*` comes from the pull request title and is kept to exactly one by `labels.yml`.

## 3. Pipeline

`ci.yml` runs on every pull request to `main` and is the only place that runs the quality commands.

| Job                   | Commands                                                                                                     |
| :-------------------- | :----------------------------------------------------------------------------------------------------------- |
| `version-consistency` | `bun run version:check`                                                                                      |
| `shared-package`      | `format:check`, `syncpack lint`, `check-types:shared`, `check-types:scripts`, `check:tailwind`, shared tests |
| `api`                 | `check-types:api`, `lint:api`, `test:api`, and `build` in `apps/api`                                         |
| `database`            | `db:migrate`, `db:generate` drift check, `db:seed --clean` on PostgreSQL 18 + Redis 8                        |
| `quality-gate`        | Aggregates the four jobs; fails unless every dependency succeeded                                            |

- CI does not run on `push` to `main`; `main` moves only through pull requests that passed.
- Required workflows carry no `paths` or `paths-ignore` filters, because a skipped workflow never reports a status and blocks the pull request forever.
- `quality-gate` uses `if: always()`; it is the single pass/fail signal.

## 4. Required Checks

Branch protection for `main` is repository configuration, not YAML. Require a pull request, require branches to be up to date, require conversation resolution, and leave force pushes and deletions disabled.

- `CI / Quality Gate` is the quality signal. Per-job checks (`CI / API`, `CI / Migrations and Seed`) exist for debugging and stay out of branch protection.
- A workflow rename invalidates its required check; update branch protection in the same change window.
- Branch protection needs admin rights, so it cannot ship through a pull request.

Required checks:

- `CI / Quality Gate`
- `Security Scan / Trivy`
- `Security Scan / Bun Audit`
- `Security Scan / CodeQL (javascript-typescript)`
- `Security Scan / CodeQL (actions)`

## 5. Release

1. `bun run release` bumps manifests, updates `CHANGELOG.md`, and opens a `chore(release): vX.Y.Z` pull request.
2. Merging it to `main` triggers `release.yml`, which tags `vX.Y.Z` and publishes the GitHub Release.
3. Pushing a `v*` tag, or dispatching with `tag_name`, produces the same result.

- `release.yml` verifies `version:check` and publishes; type checks, lint, tests, formatting, and builds already ran in `ci.yml`.
- Release notes categories come from `.github/release.yml` and `type:*` labels.
- Re-running a release is a no-op; it never deletes or rewrites an existing release or tag.

## 6. Deploy

- No deploy workflow exists until a real target with secrets and an environment does. Do not ship a placeholder that only repeats the quality gate.
- When a target lands, add `api.yml` with `push` to `main`, a `Production` environment, and the deploy steps.
- Migrations run as an explicit deploy step, never as a startup side effect.

## 7. Local Checks

`bun run check` covers type checks, lint, and Tailwind canonical classes; `bun run format:check` and `bunx syncpack lint` cover formatting and workspace manifests. Database commands need `bun run docker:up` first. Run the pipeline locally before opening a pull request and never bypass the pre-commit hook.
